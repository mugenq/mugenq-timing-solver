# Timing Solver / BeatSolver

Experimental rhythm-analysis software for recovering timing structure from music.

The current implementation estimates tempo, phase, timing sections, and beat-grid candidates from audio. Predictions are evaluated separately against osu! beatmaps, so map data is used as ground truth for evaluation rather than as input to the predictor.

## Motivation

Timing rhythm-game maps can become difficult when a song contains ambiguous transients, changing rhythmic emphasis, or multiple plausible timing interpretations. BeatSolver began as an attempt to generate an independent, interpretable timing proposal from audio that a mapper or reviewer can compare against an existing map. My own experience with timing the song https://osu.ppy.sh/beatmapsets/2624185#osu/5894459, an acoustic favorite, was enjoyable. However it can be frustrating for some people; a solver could greatly improve creative output and equalize nomination opportunity.

The goal is not to replace expert judgment, but to provide another source of evidence when timing decisions are uncertain.

## Project focus

This repository explores a practical question: how much rhythm-game timing structure can be recovered directly from audio with interpretable signal-processing methods?

The work includes:

- onset-based rhythm analysis;
- tempo and phase candidate estimation;
- local timing-section detection;
- beat-grid matching;
- one-to-one onset/grid evaluation;
- explicit separation between prediction and evaluation;
- iterative benchmarking across experimental versions.

## Results so far

Definitions
- Redline: A redline is a single point marking on the timeline of a map and has timing authority over objects at or after the redline. The chart's objects are aligned with the BPM generated by the red line. A redline can be used to denote changes in: 1) BPM timing; 2) signature. 

Saved experiments show that predicted grids can align closely with mapped hit objects once a global phase offset is accounted for.

| Version / song | Objects | Diagnostic shift | Median error | Within 10 ms | Within 20 ms | Boundary F1 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| v0.4 `sakuzyo_that_day` | 132 | -40.5 ms | 0.43 ms | 87.1% | 90.9% | 0.000 |
| v0.5 `yuyoyuppe_leia` | 346 | -36.5 ms | 3.27 ms | 79.2% | 89.3% | 0.057 |
| v0.7 `reign_of_fear` | 1,587 | -20.0 ms | 1.66 ms | 94.3% | 98.5% | 0.070 |

These results suggest that local beat-grid alignment can be strong on some tracks, while timing-section/redline detection remains substantially weaker. For example, the v0.7 benchmark places 94.3% of 1,587 mapped objects within 10 ms of the evaluated grid after a -20 ms diagnostic alignment, but its boundary F1 score is only 0.070.

These are experimental snapshots rather than a controlled cross-song benchmark: the saved runs use different songs and different versions of the algorithm. The object-error figures above are measured after diagnostic global phase alignment and should not be interpreted as general accuracy claims.

## Later research checkpoints

The repository now also includes preserved research snapshots under [`research/`](research/), with an apples-to-apples caveat table in [`research/RESULTS_COMPARISON.md`](research/RESULTS_COMPARISON.md).

Some useful checkpoints:

- A source-held-out synthetic pruning experiment retained **1,016/1,016 true events with 2,438 candidates**, about **2.4 candidates per true event**, but the same pruning rule transferred poorly to a real song. This is why synthetic recall is reported separately from real-song performance.
- A song-specific Reign of Fear proof solver achieved **1,587/1,587 mapped objects within 5 ms**, with 1.681 ms median error. Its topology and transition states were developed on that song, so it is evidence that the acoustic candidates contain enough timing information rather than a held-out generalization result.
- On the more automatic `sakuzyo - that day` experiment, the latest persisted audio-selected semi-Markov path reaches **96/132 objects within 5 ms using 8 timing points**. Candidate reset locations are substantially better than the selected path, making reset/BPM sequence selection the current bottleneck.
- Recent Cycles 14-16 test calibrated residual evidence for those resets. The latest cycle found an objective mismatch between dynamic-programming path generation and final path selection. It therefore reports a correctness fix and controlled diagnostics rather than inventing a new end-to-end accuracy number.

The comparison document keeps song-specific proofs, transfer tests, synthetic pruning, and controlled component experiments explicitly separated.

## v0.5 changes

The cleaned v0.5 line includes:

- one-to-one onset/grid matching;
- fallback sections that preserve the original global phase;
- cross-window phase comparison using actual grids at a common time;
- phase diagnostics computed before segmentation;
- continuation scoring with BPM and phase held fixed;
- onset-derived phase candidates instead of a 2,000-step brute-force scan;
- separate evaluation of the initial timing anchor and later section boundaries;
- corrected summaries, paths, benchmark output, and duplicate keys.

## Development direction

Earlier versions concentrated on direct signal-processing approaches to tempo, phase, and section detection. Iteration exposed a useful separation between problems: local beat-grid recovery can often be handled reasonably well with interpretable signal-processing methods, while detecting structural timing changes is substantially harder.

The project is therefore moving toward hybrid approaches in which conventional signal processing handles explainable rhythmic structure and learning or search methods are introduced only where they provide a clear advantage.

## Setup

```bash
python -m pip install -r requirements.txt
```

Place local audio and corresponding evaluation maps under `songs/<name>/`, then edit `song_selection` in the notebooks.

Audio files and third-party beatmaps are intentionally not redistributed.
